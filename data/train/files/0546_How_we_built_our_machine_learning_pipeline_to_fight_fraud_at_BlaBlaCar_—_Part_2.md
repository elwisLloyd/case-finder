How we built our machine learning pipeline to fight fraud at BlaBlaCar — Part 2
In this series of articles, we will share BlaBlaCar’s best practices in managing a strategic project involving machine learning. These articles do require basic knowledge in Machine Learning. Our approach is very much inspired by Google and their Google Machine Learning rule book.
If you haven’t already read it, the first part is available here.
In this second article, we will share the considerations and design we used to build our first Machine Learning Pipeline. This article is aimed at engineers or managers who want to increase the chances of success of a project involving machine learning algorithms.
PART 2 — Our First Pipeline
Get the infrastructure right
Integrating machine learning algorithms in production is always difficult. The first decision we took was to avoid putting ourselves in the critical path of the product experience. We knew we wanted to iterate fast and that it was not compatible with the Service Level Objectives expected for our trip publication and our booking funnels.
Luckily, at BlaBlaCar, we embrace the event driven architecture and we were able to leverage our Kafka cluster to listen and score publication and booking events in near real time without impacting the user experience if we happened to break our scoring service.
Each time a member is publishing a trip or booking a ride, we compute a fraud score using our business rules, some of those rules are written by experts, others are leveraging machine learning models. So for every event flowing in our Kafka cluster, we have a corresponding fraud score event. Those fraud score events are then consumed by fraud fight services that can react to high scores by canceling a trip or a booking, resetting a password, asking for additional information or even blocking a member.
When everything is going well, by the time a highly suspicious driver clicks on the publish button, we score and react to that action before the user is redirected to the next page.
Get examples to your learning algorithm
When designing a data pipeline for machine learning, it’s critical to have 3 things right:
- Features at training are correct
- Features at serving are correct
- Labels at training and evaluation are correct
Once those three things are implemented reliably and we are confident they will stay that way as we add more features and more sources of labels, then most of the work is done. We expected our first model, although very simple, to be a major leap forward in terms of detection performance. So the challenge was to minimize the risk of error as much as possible by relying on the most basic infrastructure possible, with the least amount of feature engineering.
Features at training are correct
As mentioned in the previous article, scammers may quickly adapt and bypass rules, making them useless over time. Having access to fresh and reliable features should be prioritized in that setup as the older the features are, the less they are likely to reflect the current fraud patterns on the platform.
Rule #29: The best way to make sure that you train like you serve is to save the set of features used at serving time, and then pipe those features to a log to use them at training time.
With that in mind, we decided to store all the serving features inside the fraud score event and to rely only on those features at training. This decision led to significant quality improvements and a reduction in code complexity, compared to other pipelines we have in production and that have to rely on backfill to build training sets. Relying only on production logs also removes all potential risk of data leakage.
Backfilling data is the process of filling in missing data from the past on a new system that didn’t exist before, or replacing old records with new records on an update.

What we mean by storing all serving features, is storing the encoded array that we send as input in our XGBoost or scikit-learn pipeline. No extra encoding or preprocessing should be done after the log is generated.
Features at serving are correct
Removing feature engineering from the scope of the training pipeline, means that we need to be extra careful when implementing feature engineering at serving.
At BlaBlaCar, we have access to a feature store, a key-value database relying on BigTable, that allows any backend service to retrieve historized data attached to a member or a ride. This feature store is a projection of kafka events produced by our core internal services. A design that allows any backend service to access data that would otherwise be hidden in internal databases owned by each core team. A reliable feature-store is a key component of a machine learning pipeline implemented in a microservices ecosystem.
When implementing a new feature, three scenarios are possible:
- We have enough data available in the feature store to build the new feature. In that case, we need to implement and test some real time preprocessing function that will take the feature-store response as input and expose the feature as output. 
Let’s take an example, say I would like to add a new feature to our model: the number of days since a member was registered on our platform. Searching in the feature-store, I see that the registration date of a user is available as a feature. I can simply add a java function in my serving service that will count the number of days between prediction time and the registration date. That new feature will be encoded as an integer and available in the kafka fraud score event as soon as the service is released in production, even if no rule or model is currently using that feature.
- We have enough data in kafka events produced by core teams but the data is not available in a suitable format in the feature-store. 
In that setup, we need to add a new asynchronous preprocessing function, a.k.a a kafka consumer that will be in charge of consuming kafka events and projecting them in our feature-store. Finding the most suitable projection is not always easy. Let’s say I want to have the number of messages sent by a member in the last hour as a feature of my machine learning model. Engagement team is producing a kafka event for each message sent. The simplest way to achieve this using our feature-store is to create a new feature “id of the last message sent”, each time our new kafka consumer inside our Feature Engineering Service consumes a message event, we update the id of the latest message produced by the member in the feature-store. Then, we can move to (1) and, at serving time, collect all the values of that “id of the last message sent” feature from the last hour and count the number of distinct values in that list of historized values.
- We don’t have enough data on kafka events. The core team owning that scope of our platform is not exposing the data we are looking for. The first step in that context is to meet with some representatives of the team and prioritize the exposure of that data. Once the data is available (it can take several weeks or months), we can move to (2).
Note that in all cases, the newly created feature will only be available in examples after the code in (1) is released. In the fastest setup, if a model is trained on 30 days of historical data, it will take 31 days before we can train a model on a dataset for which all examples are expected to contain a value for the new feature. In the meantime, we decided to include that feature and fill missing values with -1 value. This proved to be quite effective as long as we make sure the evaluation dataset contains examples with all features available.
Labels at training are correct
Now that we had correct features streaming in our pipeline, it was time to focus on labels.
In our case, we have 4 major sources of labels:
- From manual review following a trust and safety investigation triggered by customer ticket to customer support. Both legit and fraudulent members often try to recover their accounts by contacting the customer support.
- From solicited manual review, for some of our rules, we send a suspicious member in a queue of people waiting to be manually reviewed by agents. We also implemented random sampling strategies to assess fraud level on our platform via randomized solicited manual reviews.
- From corrective action, if for some reason a member was blocked by mistake, we can decide to unblock that member after thorough investigation.
- From our business rule, we have one label per released rule per user event. Those labels are mostly for monitoring and dashboarding but we did consider using them in our training dataset when manual generated labels are scarce. Those labels should not be used in evaluation or validation dataset.
Each label is associated with a labeling date and a member identifier. We expect to have several labels for each of our members and therefore had to build a consolidated label table that aggregates all the labels we collected on a member in a single value, to indicate if given all we know about a given member, we can consider it as a legitimate user or as a fraudster. Leveraging that table in both our reporting and dataset building tools was critical to avoid duplicated and eventually diverging aggregation logics.
When building a dashboard to monitor the labels generated by our algorithm, we will select only the label from that source, while building a dataset for training will probably involve only labels generated by manual review. Finally, in order to estimate the volume of fraud on our platform, we only keep labels generated by manual review that were solicited from the random sampling.
Using the same table for reporting and dataset building significantly increases anomaly detection in the labeling pipeline, as data scientists, data analysts and stakeholders are looking at the same data points. It’s also important to make sure a bug fix on the reporting will also fix the dataset builder.
Finally, as the label table is updated every day, we can leverage our data quality tools, monitoring distinct counts of values or null values in columns, to detect abnormal change or drop in the distribution of labels from different sources or change in the ratio in label distribution.
Conclusion
The key take-away from our project was that ensuring feature quality is the job of software engineers while ensuring label quality is a data scientist job. Using production features as a single source of features for our training pipeline is allowing us to make that clear distinction and we found that setup very powerful. For models that require far more historical data, and have to rely on backfilling, we suggest using backfilled features for the training set and rely on production features for the validation set. Which is also aligned with the recommendation of using the freshest data available in the validation set.
