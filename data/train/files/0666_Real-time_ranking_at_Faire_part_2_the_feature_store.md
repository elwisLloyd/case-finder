# Real-time ranking at Faire part 2: the feature store

Источник: https://craft.faire.com/real-time-ranking-at-faire-part-2-the-feature-store-3f1013d3fe5d

Faire relies on machine learning models to optimize ranking–enabling us to show relevant, high-quality, and personalized results to our retailers. In our last post, we outlined the ecosystem we built to train these models and deploy them online to serve real-time ranking predictions. In this article, we’ll dive deeper into one key piece of that system: the feature store. We’ll cover the following points:
- The requirements for our ML feature system, and how they address previous pain points.
- How we use both batch-computed and real-time computed features to balance predictive power and user-friendliness.
- Log-and-wait, our feature recording and ML training paradigm optimized for feature fidelity and plug-and-play models.
ML Features at Faire
In Faire’s early days, machine learning was a cottage industry: practitioners would often create their own bespoke features for each use case, design custom SQL pipelines to generate them, and run ad-hoc scripts and notebooks for model training and inference. This process, while effective enough for a small team at a startup, quickly became untenable. As the number of data scientists and ML models increased, we inadvertently duplicated many features and feature computation pipelines. There was little visibility into which features had already been defined, and it was often difficult to repurpose a feature from one model to another. Furthermore, due to the ad-hoc nature of feature computation, there was little monitoring for things like missing, unexpected, or drifting features. Finally, this kind of feature design only supported offline use cases, with no clear path towards online modeling. As we designed our real-time ranking system, we thought long and hard about how to revamp the feature creation process to address these shortcomings and enable online usage.
We specifically wanted to address the following issues:
Consolidation and discoverability. Minimizing feature duplication and encouraging reuse was a key goal for us. By having all of our features in one place, we sought to reduce load on our data warehouse from redundant queries, and make all features accessible to all models.
Ease of feature creation. In the past, feature creation had gone hand-in-hand with a one-off computation pipeline. We wanted to minimize any boilerplate associated with creating a new feature while putting up guardrails to minimize user error.
Online accessibility. A key requirement of our new system was the ability to use these features for online models. We further sought to maximize online feature availability, while minimizing the latency associated with fetching a feature.
Real-time features. Most of our past models had done offline batch predictions using non-real-time features. For real-time ranking, we wanted to make it easy for users to add real-time features such as a retailer’s last search query or last visited product.
Combinatorics. The most powerful features often involve interactions between users and items. Computing features offline for all user-item pairs is infeasible; we wanted to ensure that interaction features could be computed while avoiding this combinatoric explosion.
Monitoring by default. Monitoring is essential for ML systems, especially for those making online predictions supporting key product surfaces. By making monitoring and alerting integral pieces of our feature store, we would reduce the overhead associated with implementing a new feature, while mitigating ML failures associated with missing or unexpected feature values.

This operator enforces several key behaviors aimed at keeping our feature store clean and consistent. First, it pivots the wide-format (i.e. one column per feature) feature SQL to the long-format feature store schema: [feature_name, feature_value, identifier, datestamp]. This is critical to ensure that adding new features is possible without changing the feature store schema by adding new columns. Second, it prevents double-writing by ensuring that each entity only has a single value per feature, and by only inserting features that don’t already exist in the feature store for a given [feature_name, identifier, datestamp] combination. Finally, it enforces the requirement that all features must be registered in our enum in order to be written to the feature store.
Features can also be generated from ML models that write output to intermediate tables in our data warehouse. Adding these ML-based features to our feature store is exactly the same as above, with the feature SQL script simply selecting from the ML-generated intermediate table. The primary use case for ML-based features is in serving embeddings taken from matrix factorization- or deep learning-based models. These embeddings provide a powerful and succinct way of estimating the similarity between entities: text embeddings can be used to perform semantic search, while image embeddings can help us recommend similar products.

We rely on Airflow to orchestrate two more important tasks: feature metadata extraction and monitoring. Since we register all offline features in an enum, we can easily write these definitions to a metadata table, which includes fields like feature name, description, and author. When each feature is inserted into the feature store by the daily Airflow task, we additionally update a last_created_at field. This metadata allows us to quickly search for available features without having to scan the entire feature store. Furthermore, it allows us to whitelist certain features for certain use cases, minimizing storage overhead and improving scalability.
We also use Airflow to provide monitoring at both ends of our ML features pipeline: at batch-computation time, and after features are served and logged in online contexts (more on that below). For batch computation, we rely on the functionality of our Airflow ML feature operator to enforce constraints and log warnings. Some examples of these are: ensuring that features are not all empty or null, de-duping, type checking against our feature store schema, and logging warnings for softer instances of these (e.g. when most features are empty/null). On the other end, we do time series-based z-score monitoring of all offline and online real-time recorded feature values and counts. Together, these checks catch the following common failure modes:
- Offline feature SQL is invalid (syntax errors, etc)
- Offline feature SQL has an empty or broken upstream dependency leading to missing features
- Some change in an upstream dependency has caused a sudden change in feature values or counts
Online Feature Computation
Offline features and embeddings are computed in our data warehouse on a daily basis. To use these features for online ranking, we take a ‘best-available’ approach, fetching the latest available version of each feature within some time window. This window is tuned to maximize feature availability in case of offline computation failures while preventing excessively stale features from being used in production. We then pivot this feature set into a key: value store whose key is a Faire entity (retailer, brand, product, etc), and whose value is a list of all features and embeddings for that entity — this facilitates feature retrieval at ranking time. This map is stored on a designated Redis cluster to ensure low latency during ranking, and backed by DynamoDB in case of cache misses.
While offline features are powerful and easy to implement, certain features can only be computed in real-time. We compute online features using our main backend service, providing easy access to a wide range of data sources. For example, when a retailer signs up on Faire and completes our onboarding style questionnaire, we might compute corresponding online features by querying their responses from our production database. We also take advantage of our offline feature store to generate rich interaction features by fetching precomputed embeddings for each entity and computing similarity metrics on the fly. Finally, we cache recent retailer activity and use it to provide real-time personalization via similarities to recently viewed products, recent search queries, and more.
The design of this feature pipeline was very important to us. We wanted it to be both powerful enough to allow us to express complex features, and easy enough to enable all data scientists and ML engineers to contribute. Feature retrieval and ranking contexts
While we’ve described how we generate both offline and online features, a critical consideration we haven’t yet discussed is how we know which features to retrieve or compute, for which entities, and in which contexts. In other words: how do we only compute the features we need?
We solved this problem by defining a precise context for each ranking request processed by our backend. Recall from our earlier post that we use real-time ranking to rerank a set of several hundred candidates provided from an initial retrieval step. Our ranking context, then, includes the identities of each candidate and of the retailer making the request. Based on the use case associated with the request, we may include additional identifiers: if the request is serving a ‘similar brands’ carousel on a brand page or a ‘similar products’ carousel on a product page, we’d include the identity of the root brand or product, respectively. Once we have all relevant identifiers for a particular ranking request, we generate a set of all possible feature identifiers. Feature identifiers are either single entity identifiers like a retailer or product token, or combinations of multiple entity identifiers.
Feature identifiers are used in two ways: to retrieve pre-computed features from our online feature store, and for computing real-time features for a given context. Pre-computed features are stored in our online store using feature identifiers as keys, meaning that once we’ve generated our set of feature identifiers for a given context, we can easily fetch only the necessary features for a given request. For real-time feature computation, we first specify a set of features computers to run for a given ranking context. Then, we iterate through the set of generated feature identifiers, running all relevant computers for each, determined by the feature identifier type; e.g. for a retailer: product feature identifier, we run all retailer: product features computers. Finally, we coalesce all pre-computed and real-time features, then pass them to our model executor for inference.
Impression feature recording
So far, we’ve discussed how we generate features both offline and online for real-time ranking, but what about model training? Intuitively, ML practitioners might expect that feature computation can be applied equally for both training and inference data. However, our online features computers don’t currently support on-demand computation for arbitrary dates and entities. This was a deliberate tradeoff we made in our initial system design: we decided that the risks and complexity involved with backfilling real-time features outweighed the potential flexibility of having fully on-demand feature computation.
To train a ML ranking model in our real-time feature ecosystem, instead of backfilling features for arbitrary training data, we use a log-and-wait approach. This means that we log all precomputed and real-time computed feature values for ranked entities each time they’re served. Preparing training data, then, is a simple process: all features are already recorded for each impressed entity, and only need to be pivoted into a wide format (i.e. one row per training example). Labels such as a click or add-to-cart event are logged separately and are readily available in our data warehouse.
The log-and-wait approach has several advantages:
- No separate feature engineering is required for model training. Features must be used exactly as they were computed at request time, making model training straightforward.
- Feature consistency between training and inference is guaranteed. Because we use recorded features directly, there’s no possibility for inconsistencies between training and inference computation.
- A new model can be deployed with just a few lines of code. All features used in model training are guaranteed to already be available online, so new models are plug-and-play.
- Facilitates monitoring and altering. Because features are continually logged at inference time and streamed to a single table, feature values can be readily monitored. We’ve currently implemented null feature alerting and time series z-value anomaly detection that is applied automatically to all logged features.
We acknowledge, however, that log-and-wait isn’t perfect. Feature engineering work needs to be front-loaded ahead of model development, making it difficult to do on-the-fly optimization during training. Additionally, we’re limited in the range of training data that we can use; if we decide we need a few additional weeks of training data, we simply have to wait. Despite these drawbacks, thus far, this approach has struck a good balance of robustness, simplicity, and user-friendliness, and will continue to support Faire’s ranking models for some time to come.
