Introduction:
Recommendation systems are central to modern digital platforms, delivering personalized content by intelligently analyzing user behavior and preferences through advanced algorithms. Widely used in e-commerce, streaming services, social media, and online learning, they drive user satisfaction, engagement, and retention while supporting business growth. Typically, these systems operate using one or more of the following approaches:
- Collaborative Filtering: This approach examines user behavior by comparing how users interact with items. It identifies patterns by analyzing similar user actions. For example, if two users have watched or purchased similar items, the system will recommend those same items to other users with similar behavior.
- Content-Based Filtering: In this approach, the system analyzes the characteristics of the items themselves, such as text, images, or other features. It recommends items that have features similar to those a user has previously liked. For example, if a user enjoyed books with specific keywords, the system will suggest books with those exact keywords.
- Hybrid Approach: This approach combines collaborative and content-based filtering to enhance personalization and accuracy. It utilizes user behavior patterns in conjunction with item features, offering more personalized and accurate recommendations.
At Glassdoor, our Community Feed, Email, and Push notifications are powered by a recommendation system that follows a hybrid approach. It analyzes individual users’ behavior, such as posts, comments, and reactions, as well as the behavior of similar users, to deliver tailored, personalized recommendations. This post presents a high-level overview of the multi-stage architecture behind our system, highlighting candidate generation, filtering, scoring, ordering, and supporting infrastructure.
Glassdoor’s Recommendation System Architecture
Glassdoor’s Recommendation System follows a multi-stage architecture (Figure 1) to generate recommendations, with each stage playing a crucial role in refining the final set of relevant, personalized posts. The stages are as follows:
- Candidate Generation: This component generates the initial pool of eligible posts. It leverages user attributes and past user interactions to refine the selection. The input attributes are used to query multiple inverted indexes using techniques like Approximate Nearest Neighbor (ANN) and filter-based searches to generate candidate posts. Each inverted index retrieves posts across multiple categories, such as subscribed candidate posts (posts from followed communities or users) and public feeds (globally visible content). The outputs from these categories are merged to form the final pool of eligible candidate posts. The following (Figure 2) is a high-level diagram of the Candidate Generation component:
As shown in Figure 2, we maintain multiple types of indexes. Each contributes to the unified list of candidate posts.
Indexes are regularly updated with the latest user activity — posts, comments, reactions — to keep the data fresh. During indexing, we also compute user and post embeddings.
Embeddings are dense vector representations that capture the semantic meaning of posts and users in an N-dimensional space. A large language model (LLM) processes an input — text, image, or document — and generates an N-dimensional vector that captures its semantic meaning. Semantically similar content appears closer in vector space, enabling efficient retrieval.
For example, Figure 3 shows how sentence embeddings cluster in a 2D space. Similar meanings naturally group together, reflecting their relationships in higher dimensions. For instance, a query like “Mangoes are tropical fruits” will appear close to other fruit-related sentences in the embedding space due to their semantic similarity. This property of embeddings is fundamental to our candidate generation process, where we retrieve relevant posts based on their proximity in vector space. This proximity is calculated using the cosine similarity metric.
We evaluated multiple models from the MTEB leaderboard using performance and integration criteria to select the most suitable LLM for generating user and post embeddings. Once embeddings were computed, we identified relevant posts by calculating the cosine similarity between the user vector and post vectors.
Since an exact nearest neighbor search is computationally expensive in high-dimensional spaces, we evaluated multiple vector database solutions and chose OpenSearch as our primary vector database. Using OpenSearch’s Approximate Nearest Neighbor (ANN) search, we efficiently compute similarity scores between the input user embedding vector and all indexed post embedding vectors. Using these scores, we retrieve the top K closest vectors, ensuring high semantic relevance.
To optimize retrieval performance, we performed an A/B test comparing two embedding vector dimensions: 128 and 384. The 384-dimensional vectors outperformed 128-dimensional ones while maintaining similar latency and throughput — suggesting they capture semantic relationships more effectively without sacrificing performance.
With candidate generation complete, the pipeline moves to the next stage.

2. Filtering: Generated candidate posts are filtered and deduplicated based on business rules and user preferences. This includes removing hidden posts, flagged content, and posts marked inappropriate.
3. Scoring: The scoring stage sends filtered candidates to a pre-trained machine learning (ML) model that assigns a relevance score to each post. The scoring model is deployed as a separate service, decoupled from the main Recommendation Service. This design offers key benefits: scalability, modularity, and the ability to deploy and test different ML models independently. Separate ML models can serve other use cases for Feed, Email, and Push notifications. Figure 4 illustrates a typical post-flow through a scoring application.
ML models are packaged using MLflow, served for inference over Gunicorn, and deployed on Kubernetes clusters for scalability and orchestration. Gunicorn is optimized to handle mixed CPU/I/O workloads efficiently, supporting both real-time and batch traffic.
4. Ordering: The ordering stage applies business rules — randomization, diversification, ranking, pagination — before returning the final list of recommendations to the user. This stage also supports A/B testing to evaluate different ordering strategies. Figure 5 outlines how scored posts are transformed into the final top-K recommendations.
The modular architecture of the recommendation system presented above offers significant advantages in terms of flexibility and adaptability. This design enables us to run independent experiments (A/B tests for each stage separately), allowing effective evaluation and improvement of individual stages. It also enables independent analysis of each component’s inputs and outputs, allowing for detailed diagnostics and targeted improvements to recommendation quality. Additionally, the modular structure speeds up development by streamlining processes and enabling faster iterations. As a result, this architecture ensures that our recommendation system remains robust, scalable, and continuously optimized to deliver the best possible results.
Beyond the core pipeline, several supporting layers enhance experimentation, data access, and observability.
Experimentation Layer: The experimentation layer sits upstream of the recommendation pipeline and enables A/B or multivariate tests across stages. It integrates with Amplitude and dynamically updates request parameters based on active experiments. This setup lets us tweak request parameters for each stage, making it easy to run experiments across the entire recommendation pipeline.
For example, we can set up an A/B test to compare the performance of two different ML models in the scoring layer, which assigns scores to posts. Incoming traffic to the recommendation system is evenly split between the two variants, with 50% directed to each (or 33.33% per variant for A/B/C tests with three variants), and their performance is then measured.
Another example is conducting an A/B test in the Candidate Generation module to compare the performance of two different embedding vector dimensions for Approximate Nearest Neighbor (ANN) searches.
Data Store Layer: The data store layer contains both inverted indexes and the feature store. The inverted indexes include both embedding and non-embedding types (text-based). Each inverted index contains post data for varying time ranges, with some focusing on recent activity and others covering broader historical periods. Depending on the use case or experiment, we utilize one or more indexes to generate eligible candidate posts. Another critical component is the feature store, which serves all model features used in the scoring stage. Batch/indexing pipelines update both the feature store and inverted indexes with the latest user and post activity.
Monitoring Layer: The monitoring layer tracks input/output at each stage of the pipeline. It supports quality and performance analysis — scalability, latency, throughput, and more. It also improves developer efficiency by surfacing root causes within specific components. We use tools like Grafana, Prometheus, and Datadog for monitoring and observability.
Conclusion
In this post, we provided a high-level overview of Glassdoor’s multi-stage recommendation system. We covered how a recommendation request flows through each stage and how user behavior informs personalization. We described the role of inverted indexes, embeddings, and ANN search in generating and retrieving candidate posts. We also highlighted experimentation infrastructure used to refine relevance through A/B testing and model comparison. Lastly, we reviewed observability tools that aid debugging and performance tuning across the pipeline. As user behavior evolves and system scale grows, we continue to iterate — improving recommendation quality through A/B testing, infrastructure optimizations, ML advancements, and data-driven innovations.
